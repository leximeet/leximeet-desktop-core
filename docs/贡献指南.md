# 贡献指南

## 先找到正确层

Core 负责业务校验、判题、持久化与事务；Desktop 负责 OS 能力和窗口；Browser 负责网页交互与独立 Provider；LMCP 负责跨进程必需约束。先阅读[核心职责](1.0.0核心职责.md)，避免在界面自算分数或让插件直接写 SQLite。

提交 Issue 时，请描述可重现步骤、当前版本、预期与实际结果。提供最小脱敏样例，不上传个人资料、token、账号、网页全文或未经检查的数据库。漏洞使用[安全报告渠道](安全与隐私.md)，不公开利用细节。

## 选择贡献入口

[GitHub](https://github.com/leximeet/leximeet-desktop-core) 与 [Gitee](https://gitee.com/leximeet/leximeet-desktop-core) 平级，选择任一平台 Fork、提交 Issue 或合并请求即可。同一改动不必重复提单；若两边都已有讨论，互相附上链接，避免重复处理。维护者在同一条 main 历史中审查和整合贡献，再把相同提交同步到两个平台。

## 修改与验证

1. 保持改动集中，关键注释和文档使用简体中文，API/字段保留原文。
2. 业务变更应补充能发现行为错误的测试；事务失败、幂等重试和边界都要有负例，不能只照着实现写断言。
3. 运行[开发与测试](开发与测试.md)中的完整命令。代码变更后，Desktop 使用相同 Core 提交与 Jar 验证宿主链路。
4. 更新当前结果文档、`CHANGELOG.md` 和中文 `git-commit-message.txt`。不要将讨论、绝对机器路径、原始日志/截图或测试资料加入公开仓库。
5. 冻结协议的变更先在协议仓修订与验证，再同步到全部消费者；不能单改 Core 的随包 Schema 或只改版本名。

维护者在 main 上验收；外部贡献者可在 fork 中提交清晰的独立改动。自动化工具不代替维护者授权：不自动 push、建 PR、tag 或发布。

## 提交说明

使用明确的问题与结果，例如 `fix(core): 修复同一采集原操作重试的重复写入`。正文说明触发条件、行为、验证和限制；不粘贴对话、个人信息或大段验收日志。非语义排版单独说明，便于审查。

## 协作行为

尊重不同经验的贡献者，讨论代码与证据，避免人身攻击、骚扰或公开他人资料。维护者可隐藏泄露或骚扰内容、要求缩小改动、暂停不符合规则的贡献；项目没有承诺特定响应时限或虚构支持团队。
