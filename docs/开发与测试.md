# 开发与测试

## 日常循环

```bash
# 只应用排版，不修改冻结协议和领域资源
mvn -B -ntp -gs maven-settings.xml -s maven-settings.xml "-Dmaven.repo.local=.runtime/m2" spotless:apply
# 全部 Java 回归、格式门禁、源码 Jar、SBOM 与生产 Jar
mvn -B -ntp -gs maven-settings.xml -s maven-settings.xml "-Dmaven.repo.local=.runtime/m2" clean verify
python3 scripts/verify-docs.py
python3 scripts/verify-release.py
```

Spotless 固定 3.10.3，google-java-format 固定 1.27.0，使用现有两空格 GOOGLE 风格。关闭长字符串和 Javadoc 重流，不启用自动语义重构。Markdown/文本只检查尾空格和文件末换行；不格式化 `src/main/resources/lmcp`、领域快照和测试黄金向量。

只运行一个回归时可使用 `-Dtest=DesktopPracticeCheckpointTest test`，但交付代码仍须完整运行 `clean verify`。本仓测试不需要 GUI；Core 测试通过后，Desktop 还必须使用新 Jar 验证宿主 UI 和 Browser 的真实连接。

Windows runner 默认使用 PowerShell；Maven 的 `-D` 参数应整体引用，例如 `"-Dmaven.repo.local=.runtime/m2"`，避免属性名被拆成生命周期参数。上面的写法也适用于 Bash 和 Zsh。

| 层次 | 覆盖 | 入口 |

| HTTP / 子进程 | 动态端口、鉴权、失败边界、真实 Main 启动、拒旧/坏文件保留与安全包装异常 | `CoreServerTest`、`MainProcessTest`、`StartupDiagnosticTest` |
| 当前格式备份 | 一致快照、领域校验、授权剥离、原子恢复 | `PortableBackupTest`、`JsonBackupTest`、`BackupCapacityTest` |
| 七个业务日 | 学三天/休一天/再学三天，六模式与资料保留 | `DesktopSevenDayTest`；完整产品日常链路由 Desktop 执行 |
| 真实生产 Jar | 启动握手、未授权拒绝、状态读取、四种资料失败安全拒绝、许可/SBOM/源码与清理 | `scripts/verify-release.py` |

当前验证覆盖三种入口的查重、冻结范围内的真实干扰项、正式版协商、完整备份、拒绝预发布或损坏资料，以及现行学习流程。大型范围另由 `DesktopLargePracticeQueueTest` 使用 117,902 / 811,092 词的真实 SQLite 索引验证冷冻结在产品 15 秒请求预算内完成，保留词书排序、关联主键、回收排除与模式复用；测试不改变机器时间或延长宿主超时。准确数量以本次 `target/surefire-reports` 为准；移除实验回归后不能继续引用旧测试总数。夹具通过正式 `collect/capture/saveNote` 命令创建资料，不为测试保留已移除的接口；负向验收覆盖旧路由 404、标签命令/字段/筛选 400，以及失败不得物化词条或写入部分笔记和关系。

## 时间与资料隔离

测试使用 JUnit `@TempDir`、显式 Clock 与动态回环端口。动态文件路径通过 JSON 节点构造，不能直接拼进 JSON 字符串；Windows 的反斜杠必须保留原义。词典挂载的正常和负向请求都遵循这一规则，负向用例必须进入业务拒绝分支并校验约定的异常类型。时钟的时间推进、时区、越界路径和符号链接验证覆盖三平台；只有 POSIX 权限位专项按文件系统能力运行，Windows 测试使用 JUnit 专属临时目录继承的 ACL。需要跨日真实进程时，test profile 可以读取自身资料中的 `test-clock.json`：

```json
{"instant":"2026-10-01T00:00:00Z","zone":"Asia/Shanghai"}
```

文件只允许当前用户访问，通过原子替换推进业务时间。学习、规划、采集与提醒读取业务时间；邀请、会话、读取租约、网络期限仍使用真实时间。普通启动拒绝此开关；非法文件、符号链接或时区改变都会使测试失败，不修改操作系统时间。

测试结束时，只回收本轮创建且对应进程已关闭的资料。保留失败报告便于定位；不要遍历删除系统临时目录、正式资料、依赖缓存或其他人的日志。

## CI

GitHub Actions 配置 Ubuntu 24.04、macOS 15、Windows 2025，均使用 JDK 21；每个 job 都完整运行 `clean verify`、文档检查与真实 Jar 检查。失败也上传 Surefire 报告，成功上传候选 Jar、源码 Jar 和 SBOM，保留 14 天。Actions 固定官方提交 SHA、最小只读权限，不包含自动 tag、Release、部署或 Maven 发布。

仓库同时托管在 GitHub 与 Gitee；当前随仓自动化是 GitHub Actions，Gitee 取到相同源码后可运行上面的本地命令。本仓尚未配置 Gitee 流水线，不能把 GitHub 的运行状态当作 Gitee 已执行的证明。两平台发布均核对相同提交对应的验证结果，详见[发布与验收](发布与验收.md)。

本地 macOS 通过不代表远端三平台已通过；正式分发前须查看对应提交的实际 Actions 结果。Core 不拥有界面，Desktop 的后台 Electron UI/原生协议/连接端到端测试由 Desktop workflow 负责；Browser 独立 UI 和连接 UI 由 Browser workflow 负责。两边要锁定同一 Core gitlink 和协议摘要。
